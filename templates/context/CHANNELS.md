# Channels

Channel mechanics — true for everyone, not just us. Character limits, link placement, image specs, conventions.

**Mechanics are universal; voice is ours.** How a platform works belongs here; how we sound on it belongs in BRAND.md's per-channel adaptations. Ship reads both.

Company-level: written once, shared across that company's projects. Which of these channels are actually *on* for a given product is DISTRIBUTION.md's job, not this file's.

## Blog `[ask]`

## LinkedIn `[derive → confirm]`

Character limit and where the "see more" fold falls. **Whether links go in the body or the first comment.** Image dimensions. Hashtag convention and count.

The fold and the link rule are the two that change what gets written, so get them right.

Character limit, whether links count toward it, image dimensions and count, whether threads are used at all and how they're numbered.

## Email `[ask]`

Sending platform. Subject length before truncation, preheader length, plain or templated, list segments available.

## Case Study `[ask]`

**One artifact, four destinations.** Written once per milestone-tier feature or completed project. Each destination gets trims and extra fields — never a different piece of writing. Four separately written case studies become four drifting versions of the same story.

Canonical structure follows the Found website case study format (`https://found.fast/case-studies/logged---ai-powered-bookmarks`). That shape is the source; every other version is a cut of it. Images are shared across destinations.

**Found website** — the canonical version. Fixed structure, longest form, no length cap. All other versions are cut down from this one.

**Dribbble** — image-led. The visual carries it; text is a short supporting description. ⛔ **BLANK — verify:** shot dimensions, max file size, description character limit, images per post.

**Clutch** — client-verification oriented. ⛔ **BLANK — verify:** required fields (client name, project value band, duration, services), description limits, whether a verified client review is required before publishing.

**Contra** — portfolio project entry. ⛔ **BLANK — verify:** cover image specs, description limit, required fields.

> Do not fill those blanks from memory. Each is checkable on the platform itself, and a wrong limit produces copy that gets silently truncated.

## Build In Public `[ask]`

Communities where work-in-progress is posted publicly. The written content is the same across all of them; only submission mechanics differ.

**Two surfaces, and they are not interchangeable:**

1. **Project profile** — a one-time submission describing the product, updated at milestones. Not produced per feature. Ship touches it on milestone tier only, and usually as an *update* to an existing profile rather than a new one.
2. **Update post** — the recurring surface. Written per shipped feature, posted to the community's discussion or feed area. **This is what Ship's per-run fan-out produces.**

Only the update post belongs in the standard tier × channel fan-out.

### Built in Baltics — builtinbaltics.com

Community for builders in Estonia, Latvia and Lithuania.

*Project profile submission — verified from the submission form:*

- **Tagline:** short single line
- **Category:** dropdown (e.g. Work tool)
- **Country:** dropdown
- **Full description:** 2,000 characters, markdown supported — bold, italic, code, bulleted list, quote, link, emoji
- **Project logo:** square, JPEG / PNG / WebP / SVG, max 5 MB
- **Screenshots:** up to 4, JPEG / PNG / WebP / GIF, max 5 MB each
- **Website URL:** optional
- **GitHub URL:** optional
- **Launch & review links:** up to 8
- **Open source:** checkbox
- **Tags:** max 5

*Update post mechanics:* ⛔ **BLANK — verify.** Posted via Discussions or Town Square. Length limit, formatting support and image handling are all unconfirmed — the profile form's limits do not necessarily apply here.

### Other communities

Add as joined, each with its own subsection and the same two splits — profile and update post. The written content does not change per community; only field limits and submission mechanics do.
